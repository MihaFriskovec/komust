# Credential custody and release-approval prerequisites

_Researched 2026-09-18 for “Define credential custody and release approval.” This note records current platform facts; it does not choose komust's human custody or approval policy._

This note builds on the transport and publication contracts recorded in `maven-central-publication-transport.md` and `gradle-plugin-portal-publication-contract.md` on their research branches. Those contracts select a user-managed Central deployment and Central-before-Plugin-Portal ordering; the facts below constrain who can hold the credentials and where approval can be enforced.

## Maven Central Publisher Portal

- Publishing uses a **Portal user token**, not the interactive account password. Token generation asks for a display name and expiration date and reveals the generated credentials only once; losing them requires generating a replacement. The Publisher API represents the token as a username/password pair, base64-encodes `username:password`, and sends it as a Bearer credential. ([Generating a Portal Token](https://central.sonatype.org/publish/generate-portal-token/), [Publisher API authentication](https://central.sonatype.org/publish/publish-portal-api/#authentication-authorization))
- Authorization is user- and namespace-based. A Central organization has `Admin` and `Member` roles: admins manage members and all namespaces, while members can publish only to namespaces explicitly granted to them. Admins can invite, suspend, or remove members and grant/revoke namespace access; organization changes are audit-logged. Admins inherently have all namespace access, and that access cannot be revoked while they remain admins. ([Central organization management](https://central.sonatype.org/publish/publish-portal-organizations/))
- The token-generation documentation exposes a name and expiration, but does not document a narrower namespace or upload-versus-promote scope on the token itself. Effective publishing authority therefore follows the issuing user's current Portal access. This is an evidence boundary, not a claim that undocumented scoping cannot exist.
- The chosen `USER_MANAGED` flow uses the same authenticated Publisher API for upload/status and later promotion by deployment ID. Portal credentials are consequently capable of creating deployments and promoting a validated deployment; separating those actions in CI does not by itself create separate Sonatype privileges. ([Publisher API upload and publish operations](https://central.sonatype.org/publish/publish-portal-api/))

## PGP signing material

- Maven Central requires a detached ASCII-armored `.asc` signature for every deployed artifact and POM; signatures and checksum files are exceptions to recursive signing/checksumming. The public key must be distributed through a Central-supported keyserver so validation can find it. Sonatype currently lists `keyserver.ubuntu.com`, `keys.openpgp.org`, and `pgp.mit.edu`. ([Central publishing requirements](https://central.sonatype.org/publish/requirements/#sign-files-with-gpgpgp), [Central GPG guidance](https://central.sonatype.org/publish/requirements/gpg/))
- For Gradle CI, the fileless input set is an ASCII-armored **secret key** plus its passphrase, passed as `ORG_GRADLE_PROJECT_signingKey` and `ORG_GRADLE_PROJECT_signingPassword`, then consumed by `useInMemoryPgpKeys`. If the secret material is a signing subkey, Gradle additionally requires `ORG_GRADLE_PROJECT_signingKeyId` and the three-argument overload. Signing a `MavenPublication` automatically attaches its signatures to that publication. ([Gradle Signing Plugin](https://docs.gradle.org/current/userguide/signing_plugin.html#sec:in-memory-keys), [signing publications](https://docs.gradle.org/current/userguide/publishing_signing.html))
- The passphrase and private key together authorize artifact signing and must be treated as distinct long-lived secrets. Sonatype recommends a passphrase and says it must not be divulged; key expiration can be extended only while the holder retains the private key and passphrase, after which the updated public key must be redistributed. ([Central GPG guidance](https://central.sonatype.org/publish/requirements/gpg/))
- There is a compatibility wrinkle to resolve during setup: Gradle supports OpenPGP signing subkeys, but Sonatype's current GPG page warns that Central/Maven tooling may require signatures from the primary key. The actual chosen key shape therefore needs a preflight Central validation rather than assuming Gradle support alone proves Central acceptance. ([Gradle subkey support](https://docs.gradle.org/current/userguide/signing_plugin.html#sec:in-memory-keys), [Sonatype subkey warning](https://central.sonatype.org/publish/requirements/gpg/#delete-a-sub-key))

## Gradle Plugin Portal

- Plugin Portal publishing uses an account-level API **key and secret**. The same account key can publish multiple plugins. Gradle accepts `gradle.publish.key` / `gradle.publish.secret`, or the CI-oriented `GRADLE_PUBLISH_KEY` / `GRADLE_PUBLISH_SECRET`. ([Plugin Portal setup](https://plugins.gradle.org/docs/publish-plugin#portal-setup), [Gradle publishing guide](https://docs.gradle.org/current/userguide/publishing_gradle_plugins.html#account_setup))
- The published ownership identity is tied to the Portal account: Gradle recommends an organization/group email for organizational plugins, may require DNS proof, and communicates first-publication approval through the account email. The current public documentation does not describe a self-service per-plugin multi-user ACL. It directs plugin ownership-transfer and account-access requests to `plugin-portal-support@gradle.com`. ([Portal ownership rules](https://plugins.gradle.org/docs/publish-plugin#plugin-ids-should-trace-back-to-the-author), [Portal account and ownership support](https://plugins.gradle.org/docs/get-help))
- Because the key is account-wide and transfer is support-mediated, adding a GitHub collaborator does not grant Portal publishing authority. Additional maintainers either need a Portal ownership arrangement confirmed by Gradle support or must publish through the protected automation holding the existing account credential; the docs do not establish an automatic mapping from repository membership to Portal ownership.

## GitHub Actions approval and secret release

- Environment secrets are available only to jobs that name the environment. When required review is configured, the job cannot access those secrets until approval. Deployment branch/tag rules can separately restrict which `GITHUB_REF` values may target the environment. ([GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments))
- An environment can list up to six users or teams as required reviewers, each with at least read access, but **only one** listed reviewer must approve. The optional “prevent self-review” setting stops the run initiator approving their own deployment. Thus the native reviewer control can enforce “a different person approves” but does not by itself enforce a two-approval quorum. ([Required reviewers](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#required-reviewers))
- Administrators can bypass environment protection rules by default; the environment can instead disallow bypass for all deployments. Required-reviewer and environment-secret availability also depends on repository visibility and GitHub plan, so the repository's actual plan/visibility must be checked before treating the gate as enforceable. ([Environment bypass and plan constraints](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments))
- `GITHUB_TOKEN` permissions are independent of environment secrets. GitHub recommends granting the minimum permissions and permits workflow- or job-level `permissions`; once any permission is specified, omitted permissions become `none`. A publishing job that only checks out code and calls external registries can start from `contents: read`; GitHub release/tag mutation, package upload, or attestations should receive their additional permission only in the job that performs that operation. ([Using `GITHUB_TOKEN`](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token), [workflow permission syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions))
- Fork-originated workflows do not receive ordinary Actions secrets, and secrets are not automatically passed into reusable workflows. These defaults reduce accidental exposure but must not substitute for an environment gate on an authorized release trigger. ([Using secrets in Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets))

## OIDC and provenance boundary

- GitHub OIDC removes stored credentials only when the destination provider accepts GitHub's identity token. GitHub's `id-token: write` permission merely allows a job to request that token; it grants no other resource write access. The current Central and Plugin Portal publishing documentation instead requires their respective long-lived user token and key/secret, so GitHub OIDC does **not** replace either registry credential in the documented komust flow. ([GitHub OIDC permission](https://docs.github.com/en/actions/reference/security/oidc#workflow-permissions-for-the-requesting-the-oidc-token), [Central token requirement](https://central.sonatype.org/publish/generate-portal-token/), [Plugin Portal credentials](https://docs.gradle.org/current/userguide/publishing_gradle_plugins.html#account_setup))
- GitHub artifact provenance is an optional, separate operation. Generating a binary attestation requires `contents: read`, `id-token: write`, and `attestations: write`; it creates a verifiable GitHub/Sigstore attestation but does not satisfy Central's PGP-signature requirement or authenticate an upload to either registry. ([GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), [Central signature requirement](https://central.sonatype.org/publish/requirements/#sign-files-with-gpgpgp))

## Decisions the release policy still has to make

The platforms leave human choices open: which Central users are admins versus namespace-scoped members; whose Portal accounts own the registry credentials; whether recovery copies exist and where; how token/key rotation is exercised; whether GitHub administrators may bypass the release gate; who is eligible to approve; whether “one non-initiator” is sufficient; and whether provenance is worth the extra GitHub permissions. Those are policy decisions rather than facts supplied by the platforms.
